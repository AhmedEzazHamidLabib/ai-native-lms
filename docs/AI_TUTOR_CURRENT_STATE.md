# AI Tutor — Current State Report

Written to support a cost-architecture decision, not to sell the current
design. Describes what is actually in the code right now, in
`src/lib/tutor/*` and `supabase/migrations/0013`–`0018`. Where the
implementation differs from the original request, this says so.

## 1. Current architecture (actual request flow)

```
Student (browser)
  → TutorChat / PracticeQuestionCard (client components, useTransition)
  → Server Action: sendTutorMessage() / submitPracticeAnswer()  [src/lib/tutor/actions.ts]
  → runTutorTurn()  [src/lib/tutor/orchestrator.ts]  — the only place a turn is assembled
      1. loadSession()               — 1 query: tutor_sessions (RLS-scoped, owner-only)
      2. assessment_review re-check  — 1 query: attempts (conditional, only that entry mode)
      3. rate-limit count            — 1 query: tutor_messages count in last 5 min
      4. searchCourseMaterial()      — 1 RPC: search_course_material (Postgres full-text search)
      5. getAssessmentEvidence()     — 1 RPC: get_student_objective_evidence
      6. getPracticeEvidence()       — 1 RPC: get_student_practice_evidence
      7. formatMistakesContext()     — 1 RPC: get_attempt_mistakes (conditional, assessment_review only)
      8. history fetch               — 1 query: tutor_messages, last 12
      9. course code/title           — 1 query: courses
      → buildTutorBasePolicy() + ASSESSMENT_REVIEW_ADDENDUM/GENERAL_TUTORING_NOTE
      → getTutorProvider().generateTurn(...)   — 1 LLM CALL (claude-sonnet-5)
      10. persist 2 rows              — 1 insert: tutor_messages (user + assistant)
      11. update last_message_at      — 1 update: tutor_sessions
      12. if a practice question came back: resolveObjectiveForPractice()
          (conditional select on material_chunks) → create_practice_attempt RPC
  ← reply text + source citations + optional practice question, rendered client-side
```

**This differs from the original "Course Intelligence" framing already in
one respect worth flagging up front:** there is no precomputation step
anywhere. Every turn re-derives pedagogy (analogy choice, misconception
diagnosis, practice-question invention) from raw retrieved slide text,
using the same strong model that holds the conversation. Ingestion
(§3) does zero LLM work today — all model cost is at runtime, per
message, per student. That is the crux of the cost question in §10.

## 2. Learning objectives

- **Schema**: `learning_objectives` (`course_id, title, description,
  lecture_id, position`) — one flat table, no hierarchy, no
  prerequisite relationships. `questions.learning_objective_id` is a
  nullable FK.
- **How they were created**: NOT generated by any runtime LLM call.
  I (Claude, in-session, one time) read the real question-bank topic
  distribution (100 questions, 30 free-text `topic` strings) and the
  two lecture titles, and manually authored 7 objective names +
  descriptions, hardcoded into migration `0013_learning_objectives.sql`
  as a `do $$ ... insert ... $$` block. This is a one-time,
  design-time decision baked into SQL — running the migration again
  does nothing (idempotent via `on conflict do nothing`), and there is
  no code path that ever calls an LLM to invent or revise an
  objective.
- **Question → objective mapping**: also one-time, also in
  `0013_learning_objectives.sql` — an explicit JSON map of
  `objective title → [topic strings]`, applied via `update ... where
  topic in (...)`. Zero LLM involvement. 100/100 questions mapped,
  0 unmapped.
- **Material → objective mapping**: done by
  `scripts/backfill-material-chunks.mjs`, a **keyword substring
  match** (`OBJECTIVE_KEYWORDS` — a hardcoded list of lowercase
  strings per objective, e.g. `"binary", "bit", "byte", "ascii"`) run
  against each slide's concatenated title+text+notes. No embeddings,
  no LLM. Best-effort: 21/28 CSE 1203 slides matched an objective, 7
  didn't (mostly intro/agenda slides) and are left `NULL` rather than
  forced into a wrong bucket.
- **Runs once vs. repeatedly**: everything in this section is
  ingestion/migration-time, run once per course/material version, never
  per student message. This part of the system is already "cheap" in
  the sense the hybrid design wants — it's just not *smart* (no
  pedagogical reasoning, just keyword matching).

## 3. Material processing (what happens today when a PPTX is ingested)

Unchanged from before this milestone, reused as-is:

1. **Parsing** (`src/lib/ingestion/pptx.ts`) — deterministic ZIP/XML
   walk, no OCR, no LLM. Produces `{index, title, text, speakerNotes}`
   per slide.
2. **Storage** — one row per slide in `slides` (pre-existing table).
3. **Chunking** (`scripts/backfill-material-chunks.mjs`, new this
   milestone) — one `material_chunks` row per **published** slide,
   verbatim title+text+notes concatenated. No sub-slide splitting, no
   summarization, no rewriting.
4. **Embeddings** — **none**. A `vector(1536)` column exists on
   `material_chunks` but is never written or read. Retrieval is
   Postgres `tsvector`/`ts_rank` full-text search.
5. **LLM analysis** — **none, anywhere in ingestion.**
6. **Learning-objective assignment** — keyword match, described above.
7. **Provenance** — `material_chunks` carries `lecture_id, material_id,
   material_version_id, slide_id, position`, enough to cite "Lecture 2
   · Slide 18" truthfully.

**External AI/API cost incurred by ingestion today: $0.** This is the
single clearest fact for the cost conversation — all model spend is
concentrated entirely in the per-message runtime path, none in
one-time processing.

## 4. Per-tutor-message pipeline (concrete walk-through)

Student sends: *"What is the difference between RAM and storage?"*

- **DB queries**: ~9 round trips as enumerated in §1 (session load,
  rate-limit count, 3 evidence/retrieval RPCs, history fetch, course
  lookup, message insert, session-timestamp update). All are indexed
  point lookups or small aggregations — none are expensive queries,
  but it is 9 sequential-ish network round trips to Postgres per
  message before the model is even called.
- **Embedding calls**: 0 (no embeddings anywhere in this system).
- **LLM calls**: **exactly 1**, to `claude-sonnet-5`, via a forced
  tool call (`tool_choice: {type: "tool", name: "tutor_turn"}`). If
  the model decides to issue a practice question, that is returned as
  a field (`practiceQuestion`) in this SAME call — no second call.
- **Context sent** (this message, mid-conversation):
  - System policy: ~645 tokens (`buildTutorBasePolicy` + one addendum
    paragraph), **identical text on every single message**, never
    cached.
  - Retrieved material: up to 4 chunks (`limit: 4` in
    `runTutorTurn`), each a full slide's raw text — commonly
    150–400 tokens per chunk, so **roughly 600–1600 tokens**,
    re-fetched and re-sent fresh every message even if the same
    chunks were just sent last turn.
  - Student evidence summary: a handful of one-line
    `"Objective: assessment X/Y; practice A/B"` strings — small,
    usually under 150 tokens.
  - Conversation history: up to the **last 12 messages**
    (`HISTORY_LIMIT`), sent as full text every time. Early in a
    session this is small; by message 12+ this is the single largest
    and fastest-growing cost component, and it is sent in full on
    every subsequent turn with no summarization and no caching.
  - Output: `max_tokens: 1024` ceiling; actual replies in testing ran
    ~100–300 tokens.
  - **Rough total input for a mid-conversation turn: on the order of
    2,000–3,500 tokens, before the model has written anything** —
    and this is paid on *every* turn, not just the first.
- **Model**: `claude-sonnet-5` — the same model for every
  conversational turn regardless of whether the question is trivial
  ("hi") or requires real reasoning.

## 5. Performance → Tutor pipeline

Student is weak on Binary & Bits (0/2 on the real graded assessment) →
clicks "Practice with AI":

1. `startTutorSession({entrySource: "performance", learningObjectiveId})`
   — `findOrCreateTutorSession` (reuses an existing session for that
   objective if one exists; otherwise 1 insert) + loads message
   history (1 query). **No model call yet.**
2. Client auto-submits a synthetic kickoff message ("I struggled with
   Binary, Bits & Bytes... can you help me practice it?") through the
   exact same `sendTutorMessage` path as §4 — **1 LLM call**, same
   model, same context shape, evidence summary now includes the real
   0/2.
3. Conversation proceeds turn by turn exactly as §4 — **1 LLM call per
   student message**, no different pipeline for "performance-sourced"
   sessions vs. direct ones beyond which evidence line is emphasized.
4. When the model issues a practice question (same call, tool field),
   student answers:
   - Numeric/short-text: `submit_practice_answer` RPC does exact-match
     comparison in SQL. **0 model calls.**
   - Free-text "explanation": `submit_practice_answer` returns
     `pending_evaluation` + rubric text; `submitPracticeAnswer()`
     (`src/lib/tutor/practice.ts`) makes **1 LLM call** to
     `claude-haiku-4-5-20251001` (cheap/fast model, already split out
     from the conversational model) to get `{correct, reason}`, then
     1 RPC to persist it.

**Total for one full Performance→Tutor→Practice loop: 2–4 Sonnet calls
(kickoff + however many conversational turns) + 0–1 Haiku call**,
depending only on how long the conversation runs, not on anything
precomputed.

## 6. Providers / models

- `src/lib/tutor/provider.ts` — `TutorProvider` interface,
  `AnthropicTutorProvider` the only implementation, raw `fetch` to
  `https://api.anthropic.com/v1/messages` (no SDK dependency).
- Two model constants, **hardcoded in this one file**, not env-driven:
  `TUTOR_MODEL = "claude-sonnet-5"` (conversation),
  `EVAL_MODEL = "claude-haiku-4-5-20251001"` (explanation grading only).
- **Different tasks already use different models** — this split
  exists today, but only for the narrow "grade a free-text practice
  answer" task. The actual tutoring conversation (the expensive,
  high-volume part) always uses the stronger model.
- **Preprocessing-with-strong-model / runtime-with-cheap-model does
  NOT exist today** — there is no preprocessing step at all (§3), and
  the runtime conversational path uses the *stronger* model, not a
  cheap one, for every turn.
- **Difficulty of changing this**: low, structurally. `getTutorProvider()`
  is the single call site every consumer goes through
  (`orchestrator.ts`, `practice.ts`); swapping which model
  `generateTurn` uses, or adding a third model constant for a new call
  shape, means editing this one file. The harder part isn't the
  provider plumbing — it's that `generateTurn`'s system prompt
  currently assumes the model must reconstruct pedagogy from raw
  material every time (§10 gets into what changes if that assumption
  changes).

## 7. Cost model (architectural, not fake-precise)

**ONE-TIME (per material version)**
- Parsing, chunking, objective-keyword-matching: **$0** (deterministic
  code, no external API).
- Embeddings: **$0** — none exist.
- Pedagogical analysis: **$0** — none exists. *(This is the empty box
  the hybrid design in §10 would fill.)*

**PER-STUDENT / PER-MESSAGE (the entire current cost surface)**
- Every tutor message: 1 Sonnet call, ~2,000–3,500 input tokens
  (growing with conversation length up to the 12-message cap), no
  caching.
- Every practice-question generation: **free** — folded into the same
  Sonnet call as the surrounding message, not a separate cost.
- Every deterministic (numeric/short-text) practice evaluation:
  **$0** — SQL only.
- Every free-text practice evaluation: 1 Haiku call, small
  (~200–400 tokens).

**What unnecessarily repeats expensive reasoning**: the same
model that holds the conversation is asked, on every single turn, to
re-derive *how to teach this concept* from scratch off raw slide text
— the analogy, the misconception framing, the practice-question idea —
none of which changes between one student's session and the next
covering the same objective. 50 students each asking about Binary &
Bits pay for the "invent the switch analogy" reasoning 50 separate
times (more, across their turns), instead of once.

## 8. Context size (typical mid-conversation turn)

| Component | Approx. tokens | Repeated every turn? |
|---|---|---|
| System/tutor policy | ~645 | Yes, verbatim, uncached |
| Retrieved chunks (≤4) | ~600–1,600 | Yes, re-fetched + re-sent even if unchanged |
| Student evidence summary | ~50–150 | Yes, small |
| Conversation history (≤12 msgs) | grows to the largest component | Yes, full text, no summarization |
| Student's new message | ~20–80 | N/A |
| **Total input, mid-conversation** | **~2,000–3,500** | — |
| Output ceiling | 1,024 max | typically 100–300 actual |

**Biggest reduction opportunities, in order**: (1) prompt-caching the
system policy — it is byte-identical across every turn, every
session, every student, and currently paid for fresh every time;
(2) not re-sending full history text every turn — either cache it or
summarize older turns; (3) not re-deriving retrieval + full pedagogy
reasoning per turn at all, which is exactly what §10 addresses.

## 9. Eliana-JARVIS ideas — what was actually used

Documented already in `docs/AI_TUTOR_ARCHITECTURE.md` §11. Two ideas
adopted, deliberately scaled down:

1. **Structural separation of internal signal from user-facing text**
   — Eliana's Thinking pass returns a JSON "constraint map" with the
   chat-facing answer as one field among several internal ones. The
   tutor's `tutor_turn` tool call mirrors this in miniature:
   `{reply, teachingMove, practiceQuestion?}` — only `reply` is ever
   rendered.
2. **Every context source gets an explicit semantic role** — directly
   justifies the four labeled blocks (SYSTEM POLICY / RETRIEVED
   MATERIAL / STUDENT EVIDENCE / HISTORY) instead of one blended
   prompt string.

**Explicitly not adopted**: Eliana's separate evaluator pass (a second
model call judging the first response — would have doubled cost per
turn, rejected specifically for that reason), phi/affect state,
identity/memory systems. Nothing about Eliana's architecture
addresses today's core cost question (precompute vs. per-message
reasoning) — that idea comes from your Course Intelligence proposal,
not from Eliana.

## 10. Feasibility of the "Course Intelligence" hybrid — evaluation only, not implemented

**Feasibility with the current architecture: high — this is an
additive extension, not a rewrite.** The existing spine was built
exactly where this hybrid needs it to be:

**What already built remains directly useful, unchanged:**
- `learning_objectives` — the natural key for precomputed intelligence
  to hang off. No schema change needed to *reference* it.
- `material_chunks` + `slides` + `material_versions` — stays exactly
  as-is as the raw factual source of truth and citation/provenance
  layer. `material_versions` is already immutable-and-versioned
  (Invariant 6), which is precisely the invalidation trigger a
  precompute step needs — "new `current_version_id`" is already the
  exact moment the schema marks as "this content changed."
- `search_course_material` RPC — stays as a fallback/verification
  layer exactly as you asked about: grounding precomputed claims back
  to real slide text when needed, and handling genuinely out-of-scope
  questions the precomputed intelligence didn't anticipate.
- `get_student_objective_evidence`/`get_student_practice_evidence` —
  unchanged; personalization layer is orthogonal to where pedagogy
  comes from.
- `tutor_sessions`/`tutor_messages`/`practice_attempts` schema and all
  RLS/authorization boundaries — **completely unaffected**. Security
  posture doesn't change based on which model tier answers.
- UI (`TutorChat`, `PracticeQuestionCard`) and the
  Server Action layer (`actions.ts`) — unaffected; they consume
  `{reply, sources, practiceQuestion}` regardless of how that shape
  was produced.
- `TutorProvider` abstraction — already supports multiple models
  (§6); adding a third "precompute" call shape is additive.

**What would actually change:**
- A new table, e.g. `learning_objective_intelligence` (keyed by
  `learning_objective_id` + `material_version_id` or a version marker),
  holding: canonical explanation, 2–3 analogies, common misconceptions,
  practice-generation guidance/templates, difficulty notes, and
  (if wanted) a `depends_on uuid[]` self-reference on
  `learning_objectives` for prerequisite relationships (currently
  absent — objectives are a flat list today).
- A new one-time job (parallel to `backfill-material-chunks.mjs`) that
  calls a **stronger** model once per objective per material version,
  reading the relevant `material_chunks`, and writes structured output
  to that table. This is the only new AI spend, and it happens at
  publish time, not per student.
- `runTutorTurn`'s system-prompt construction changes: instead of
  handing raw retrieved chunks to the model and asking it to invent
  pedagogy, it would primarily hand the **precomputed** explanation/
  analogies/misconception list for the relevant objective, using raw
  `search_course_material` chunks only as a citation source or a
  fallback when the precomputed material doesn't cover what the
  student asked.
- `TUTOR_MODEL` for the conversational path could drop to a cheaper
  model (e.g. Haiku), since its job shrinks from "reconstruct
  pedagogy AND converse" to "converse using pre-supplied pedagogy" —
  much closer to what Haiku already does well for practice evaluation.
- Practice-question generation could move from "invent freely, every
  time" to "fill a precomputed template/guidance with fresh numbers,"
  which is exactly where a cheap model (or even non-LLM code) becomes
  viable for that specific sub-task.

**Cost advantage**: the expensive reasoning (analogy selection,
misconception cataloguing, practice-generation strategy) is paid once
per objective per material version instead of once per student per
turn. At classroom scale (tens of students, many turns each), this is
the difference between ~7–10 expensive-model calls total (one per
objective) and hundreds of expensive-model calls (current
architecture) — with the per-message runtime cost dropping to
cheap-model pricing for the bulk of the volume.

**Quality disadvantage / risk**: precomputed pedagogy is static per
version — it can feel canned if reused verbatim across students, and
a cheap runtime model is weaker at handling a student's genuinely
novel misconception that the precompute step didn't anticipate.
Mitigation, matching what you asked about directly: keep
`search_course_material` as a live fallback/verification path (already
built, no change needed) for (a) questions the precomputed
intelligence doesn't cover, and (b) grounding/citation so the cached
pedagogy doesn't silently drift from the real source material over
time.

**Invalidation on material updates**: falls out of the existing
versioning invariant for free — regenerate
`learning_objective_intelligence` rows when `materials.current_version_id`
changes, exactly the same trigger point `backfill-material-chunks.mjs`
already reacts to (it re-chunks on every run; a precompute job would
re-analyze only objectives touched by the new version).

**Interaction with learning objectives**: strengthens the spine
argument rather than complicating it — `learning_objective_id`
becomes the join key for four things instead of three (materials,
assessment evidence, practice evidence, *and* precomputed pedagogy),
which is the "common thread" framing from the original brief, made
more literal.

**Recommendation for the decision, not a directive**: this is worth
doing before this feature sees real classroom volume, specifically
because the current per-message reasoning cost scales with
(students × turns), not with (objectives), and objectives are fixed
and small (7 today) while turns are not.
